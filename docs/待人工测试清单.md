### 本轮新增实现的三个模块

**PIN 配对加密**（`crates/kanami-net/src/crypto.rs`）
- 4 位 PIN 经 PBKDF2（20 万轮）派生 32 字节密钥，加了盐防止跨会话撞钥
- 音频负载用序号绑定的密钥流加密，包头保持明文（让接收端不解密就能做丢包检测）
- 拒绝序号回退的包，防重放
- 自动生成的 PIN 排除 0000/1234/1111/9999 这类一眼能猜的组合

**端到端延迟测量**（`crates/kanami-net/src/clock.rs`）
- 用 Ping-Pong 四点时间戳估算两端时钟偏移（NTP 简化版）
- 保留最近 16 次采样，取往返最快的那次——路径最干净，估计最可信
- 同步之后才能把「发送端采集时刻」换算到本机时间轴，算出真实延迟
- 上一次交付里显示的只是本地缓冲时间，现在能给出端到端数字

**Android 前台服务**（`PlaybackService.kt`）
- 常驻通知 + 停止按钮，锁屏/切后台不再断流
- `foregroundServiceType="mediaPlayback"`（Android 14 要求）
- 已验证：`dumpsys activity services` 能看到 `ServiceRecord{... .PlaybackService}`

**Rust 侧入口已接上**（本轮补完）：
- `src-tauri/src/playback_service.rs`，用 JNI 调 Kotlin 的静态方法
- 连上音源时启动服务（通知标题带对端设备名），断开且无音源时停止
- 只在 `cfg(target_os = "android")` 下编译，桌面构建完全不受影响
- 用 jni 0.21 而不是 0.22：0.22 把 JNIEnv 拆成 Env/EnvUnowned 变成回调式 API，
  而我们只需要「附加线程 → 调静态方法」这个最简单的用法
- `lib.rs` 的 `forbid(unsafe_code)` 改成 `deny`：forbid 无法被子模块覆盖，
  而这个模块必须用 unsafe 才能做 JNI。每处 unsafe 都写了安全不变量。

**Android 构建必须用环境变量**：Tauri CLI 会覆盖 `.cargo/config.toml` 里的 linker，只有 `RUSTFLAGS="-C linker=.../aarch64-linux-android26-clang"` 能压住。不带 API 26 会因找不到 `-laaudio` 链接失败。

## 本轮（第 1 轮续）新增修复

### ✅ 修掉的真 bug：多音源连接会互相覆盖

`connect_to_peer` 里把 `stream_id` 写死成 1，接收线程又把所有来的包投给 `incoming` 列表的 `first_mut()`。**接第二台音源时，两路数据会挤进同一路抖动缓冲**——「一播放端接多音源」这个核心需求实际上是坏的。

修法：`AppState` 加 `next_stream_id` 原子分配器，每路一个新号；接收线程按 `stream_id` 精确定位；`disconnect` 按 `device_id` 找到对应那一路再移除。补了 3 个回归测试锁住行为。

### ✅ 修掉的 CI 问题（三层，逐个击破）

1. `actions/setup-node` 的 `cache: pnpm` 要求它自己探测 pnpm store，在 pnpm 刚装好没 install 过时探测失败 → 改用 `actions/cache@v4` 显式缓存 store。
2. pnpm 12 默认阻止依赖执行安装脚本，esbuild 的 postinstall 被拦 → `pnpm install --frozen-lockfile` 报 `ERR_PNPM_IGNORED_BUILDS` → 在 `pnpm-workspace.yaml` 的 `allowBuilds` 里放行 esbuild。
3. 修复后本地 `pnpm install --frozen-lockfile` 与 `pnpm build` 均通过。

**CI 当前状态**：最新一次运行仍在 GitHub 队列里等 runner（免费额度高峰），不是失败。

## 本轮（第 2 轮续）修复的三处致命缺口

前两轮把模块写完了，但**没人调用**——审计发现三个功能实际上是死的。这一轮全部接上并验证。

### 1. 发送泵从未被调用

`start_sending` 把采集回调接进了环形缓冲，但主循环从来不把缓冲里的样本喂给编码器。**采到的音频永远躺在缓冲区里，一个 UDP 包都发不出去。**

修：主循环每 20ms 调一次 `pump_capture`（正好是标准档一帧）。

### 2. 播放器从未启动

接收端把混音结果推进了 `SharedOutput`，但没有任何东西把它送进声卡。**收到的音频会被解码、混音、然后静默丢弃。**

修：单独起一个播放线程持有 cpal Stream（它是 `!Send`，进不了 Tauri 的 managed state）。实测日志：`播放器已启动：MacBook Pro扬声器 48000Hz 2ch`。

### 3. 加密有安全漏洞（端到端测试抓到的）

错误 PIN 时 `SecureChannel::open` 返回 `Ok` 并给出垃圾数据，接收端把这些噪声当音频播出去——**实测峰值 1.168，是可听见的噪音**。用户启用 PIN 配对后，监听者猜错 PIN 反而会听到噪声，这比静音更糟。

修：加 8 字节认证标签，覆盖序号与密文；验签用定时安全比较；解密失败补静音。

```
正确 PIN  相关系数 1.0000
错误 PIN  相关系数 0.0000，峰值 0.000（静音而非噪声）
```

## 本轮（第 3 轮续）：换真机测试，挖出三个「Mac 上永远测不出来」的缺陷

前两轮所有验证都跑在 Mac + BlueStacks 模拟器上。这一轮接了真机
（Redmi 2602BRT18C / Android 17 / arm64），三个缺陷立刻暴露。
**每一个都足以让功能完全不可用**，而单元测试和同机 e2e 全部是绿的。

### ✅ 已修：音源端从不收包，一个音频包都发不出去

`AudioSocket::send` 在 `peer` 为 `None` 时静默返回 `Ok(false)`。
`peer` 只能靠「从收到的包里学」，而音源端从来没在主循环里调过 `try_recv`。

结果：编码器在跑、序号在涨、日志一片正常，实际对端什么也收不到。

为什么一直没发现：`e2e` 和 `connect_cli` 例子都用 `set_peer` 手动填了地址，
把这条真实路径整个绕过去了。

### ✅ 已修：信令读包阻塞了 20ms 主循环

`accept_signals` 直接在主循环里做阻塞 `read_exact`。
只要有一个客户端连上却不发数据（端口扫描、浏览器预连接、对端写完就崩），
整个应用就停摆：不广播、不收音频、不推状态。

表现：「应用还在，但谁都连不上，界面数字全冻住」。

### ✅ 已修：Android 上 accept 出来的 socket 是非阻塞的

Linux 的 `accept()` 会继承监听 socket 的 `O_NONBLOCK`，macOS **不会**。

于是同一段代码在 Mac 上好好的，到手机上变成：
TCP 连得上、数据也发出去了，服务端 `read_exact` 立刻 `EAGAIN` 失败，
被当成超时丢掉——「应用在跑，但谁都连不上」。

修复：`accept` 之后显式 `set_nonblocking(false)`。

### 回归测试

| 测试 | 锁住的缺陷 |
|---|---|
| `没有对端时发送返回未发出` | peer 学习缺失 |

### ✅ 新增完整链路验证（`full_chain`）

之前的 `e2e` 用手搓的收发循环，把引擎层真实的类整个绕过去了——
能证明「协议对」，证明不了「接线对」。

`full_chain` 走真实路径：播放端先被回绝 → 音源端记下待确认设备
→ 授权后重连拿 `Accept` → 音源端从收到的包学到播放端地址
→ 编码发送 → 抖动缓冲解码 → 量峰值与 RMS。

三档实测（源信号是 0.5 幅度正弦，RMS 理论值 0.3536）：

| 模式 | 包数 | 帧数 | 丢包 | 峰值 | RMS |
|---|---|---|---|---|---|
| 标准 | 180 | 175 | 0 | 0.5043 | 0.3535 |
| 低延迟 | 190 | 189 | 0 | 0.5062 | 0.3487 |
| 高音质 | 179 | 170 | 0 | 0.5031 | 0.3536 |

三档 RMS 全部对上理论值，说明链路无增益失真、无静音假通过。

## 本轮（第 4 轮）：真机跨设备链路已打通，但入站仍被厂商 ROM 拦

### 重大进展：手机当播放端可以完整工作

之前所有跨设备测试都卡在「Mac 连不上手机」。换了方向之后发现：
**这不是死路，方向反了而已**。

本项目从第一天起就是 NAT 驱动的设计——**连接由播放端发起**。
手机当播放端时，它是**主动外连**的一方，完全不受入站拦截影响。

实测证据链（手机 → Mac 音源，全通）：

| 环节 | 结果 |
|---|---|
| 手机 TCP 连 Mac 信令端口 | 建立耗时 0.00s |
| Join 握手 | 收到 `Accept`，拿到音频端口 |
| 手机 UDP 发 Hello | Mac 学到 `对端=Some(192.168.3.148:43128)` |
| Mac 回送音频 | 手机侧收到成串 `KM\x01\x03` 帧（kind=3 Audio） |

也就是说：**「手机当播放端接电脑音源」这条主路径是通的**，
「电脑当播放端接手机音源」受厂商 ROM 拦截（见下）。

### 已修：两个让自动发现在安卓上彻底失效的缺陷

1. **没有 MulticastLock** — Android 默认在驱动层丢弃 UDP 广播/组播以省电，
   只有应用持有 MulticastLock 时才交给用户态。
   `WifiService: acquireMulticastLock uid=... lockTag=kanami-discovery` 可验证。

2. **发现端口被独占** — 原来直接 `UdpSocket::bind(47821)`，
   第一个进程占住后其它进程只能退回临时端口，
   于是「同机两个实例互相发现」永远失败（诊断探针也因此看不到应用）。
   改用 socket2 同时开 SO_REUSEADDR + SO_REUSEPORT。

双实例实测：

```
✓ Mac 测试音源 [test-source-001] 音频=58885 信令=61919 方式=广播
✓ 所有设备的端口都已正确通告
```

### 仍阻塞：本机（小米/HyperOS）拦截第三方应用的入站流量

| 测试 | 结果 |
|---|---|
| Mac → 手机 adb 端口 40541 | 通（adbd 跑在系统 UID） |
| Mac → 手机 shell 开的端口 18892 | 通 |
| Mac → 手机**应用**端口（多个） | SYN 根本不到（`/proc/net/tcp` 全程只有 `0A` LISTEN） |
| Mac → 手机**应用** UDP 47821 | rx_queue 恒为 0 |
| 手机 → Mac 出站 TCP/UDP | 全通 |

结论：不是代码问题。需要在手机上放开：
**设置 → 应用管理 → Kanami → 网络助手**（允许联网/后台），
或关闭「安全中心 → 网络助手」的省流量限制。

### 新增工具：`test_source` 例子

一个可自动批准的测试音源端，跳过 macOS 的 TCC 录音授权
（那个必须人工点，无法脚本化），直接验证信令与音频通道。

## 第 4 轮补充：中文输入法全角字符（已修并验证）

### 问题

在手机上填 `192.168.3.149:58893`，输入法把点号和冒号打成全角：
`192。168。3。149：58893`。直接 `str::parse::<SocketAddr>` 必然失败，
而用户看着屏幕觉得「我明明填对了」。

**用户用中文输入法打全角字符是正常的**，不该让他们自己找原因。
手动 IP 是广播被拦时唯一的连接方式，它坏在这里等于把最后一条路也堵死。

### 修复

新增 `addr` 模块做容错解析：

| 输入 | 处理 |
|---|---|
| `192。168。3。149：58893` | 全角 `。．：` → 半角 |
| `  192.168.1.10:47822  ` | 去首尾空白 |
| `http://192.168.1.10:47822/` | 忽略协议前缀与路径 |
| `192.168.1.10` | 补默认发现端口 |
| `不是地址` | 报错（不静默接受） |

6 条测试锁住每一类输入。

### 真机验证

输入框：`192。168。3。149：58893`（全角）
设备列表：`手动设备 192.168.3.149:58893`（已归一化）
点连接 → 日志 `收到连接请求 → 准备连接 → 发起 TCP 连接`

错误提示也确认可见：`连接失败：connection timed out` 常驻横幅
（这是之前修的 NoticeBar，不再是点了没反应）。

## 第 4 轮关键修复：移动端采集原来是假的

### 缺陷

`capture_android.rs` 和 `capture_ios.rs` 的 `start()` 只做一件事：
按 10ms 节拍推**全零样本**。

时序对、生命周期对、「正在发送」也显示得出来、
日志还打印「开始发送，音源=麦克风」——
唯独没有真实声音。这是最难被发现的一类缺陷：
所有指标都正常，只有对面听着安静。

### 修复

换成 cpal 真实采集（`capture_mobile.rs`）：

- Android 走 AAudio（API 26+），iOS 走 CoreAudio —— 系统推荐的实时路径
- 设备常见 44.1kHz（实测这台就是 `2ch 44100Hz`），项目内部统一 48kHz，
  所以加了线性插值重采样。不做这步音高会整体偏移。
- 采集起不来时 `start()` 直接返回错误，
  而不是让界面一直显示「正在发送」却没有任何声音。

### 真机验证

```
dumpsys audio:
  active? true
  source client=VOICE_RECOGNITION, dev=2ch 44100Hz, uid:10452,
  pack=com.szzz666.kanami, silenced:false
```

修复前**根本不会有这个录音会话**。`silenced:false` 说明不是静音。

### 5 条新测试

| 测试 | 锁住的行为 |
|---|---|
| 降混把立体声取平均 | 多声道 → 单声道 |
| 同采样率时只做声道复制 | 不做无谓重采样 |
| 重采样保持时长大致不变 | 4410@44.1k ≈ 4800@48k |
| 重采样保持幅度 | 直流信号仍是 0.5，无增益失真 |
| 空输入不会崩 | 边界安全 |
