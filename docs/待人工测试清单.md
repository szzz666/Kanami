## 需要你验证的

### B1. macOS 音频授权（**最关键的阻塞项**）

**为什么必须你来**：TCC 授权弹窗只在 GUI 会话里出现，我的自动化点击点不中 WebView 内的 DOM 按钮。

**步骤**：
1. 打开 `target/release/bundle/macos/Kanami.app`
2. 如果有弹窗问「允许 Kanami 录制系统音频」→ 点**允许**
3. 如果没弹窗：系统设置 → 隐私与安全性 → **麦克风** 和 **屏幕录制** 里都勾上 Kanami
4. 完全退出应用再重开
5. 「发送」页点「开始发送」，放一首歌

**通过标准**：
- 「已发送帧」数字持续增长
- 日志（`log stream --predicate 'process == "kanami"'`）出现「开始采集」
- 若 6 秒无数据会提示缺权限

### B2. 在 Mac 上点「允许」完成首次配对

上一轮跑 `connect_cli` 时弹窗还在。重跑一次然后点允许：

```bash
SIGNAL_PORT=$(lsof -iTCP -P | grep kanami | grep LISTEN | head -1 | sed 's/.*://' | cut -d' ' -f1)
cargo run -p kanami-net --example connect_cli -- 127.0.0.1:$SIGNAL_PORT 5
```

**通过标准**：点允许后，命令输出从「尚未确认」变成「✓ 信令握手成功」并打印对端设备名与音频端口。

### B3. Android 手动连接 Mac（UI 路径）

**为什么没测成**：`adb shell input text` 无法写入 antd-mobile 的受控 Input 组件（React 不认这种合成输入），所以 UI 上填不进地址。

**步骤**：Android「接收」页点「+」→ 点输入框 → **用屏幕键盘手动输入** `192.168.31.45:<Mac 的信令端口>` → 点「添加」→ 点该设备的「连接」。

**通过标准**：连接成功后，Mac 上点允许；Android 混音台出现一路音源，手机能听到 Mac 放的声音。

### D1. 三档模式的实际听感差异

分别用三档模式播放同一段音乐。

| 模式 | 应用内「缓冲」显示 | 预期端到端 |
|---|---|---|
| 低延迟 | **固定 20ms，不增长** | 60–80ms |
| 标准 | 40–120ms 自适应 | 120–150ms |
| 高音质 | 60–200ms 自适应 | 180ms 左右 |

低延迟档的缓冲数字如果自己涨了，就是 bug（有单测守着，但需要真实网络确认）。

### D2. 一播放端接多音源（混音台）

两台 Mac 都当音源，第三台当播放端。播放端依次连两个。

**通过标准**：两路同时出声互不打断；每路音量/静音/独奏生效；拔掉一路网络，另一路不受影响；接满 4 路不爆音。

### D3. 本机同时收发是否啸叫

Mac A 发给 Mac B，同时 B 也发给 A，两边喇叭都开。

**通过标准**：**不应啸叫**。macOS 的采集会排除本进程。若啸叫，检查日志里是否有「已解析本进程音频对象 id=…，将从采集中排除」。

### D4. 局域网自动发现

两台设备同一 Wi-Fi，打开等 10 秒。

**通过标准**：互相出现在列表（≤5 秒）；关掉一台约 8 秒后消失；点「扫描」立即刷新。

**已知限制**：模拟器上广播和组播双向都不通（已实测），所以在 BlueStacks 上必然只能手动添加。

### D5. 托盘行为

点窗口关闭按钮。

**通过标准**：窗口消失但进程还在；菜单栏有图标；托盘菜单可显示主窗口 / 开始停止发送 / 退出。

### D6. 输出设备切换

设置页切内建扬声器 ↔ 蓝牙耳机。

**通过标准**：声音从新设备出来，无杂音。默认输出是 44.1kHz 蓝牙，48kHz 重采样路径必须正确。

### 本轮新增实现的三个模块

**PIN 配对加密**（`crates/kanami-net/src/crypto.rs`）
- 4 位 PIN 经 PBKDF2（20 万轮）派生 32 字节密钥，加了盐防止跨会话撞钥
- 音频负载用序号绑定的密钥流加密，包头保持明文（让接收端不解密就能做丢包检测）
- 拒绝序号回退的包，防重放
- 自动生成的 PIN 排除 0000/1234/1111/9999 这类一眼能猜的组合

**端到端延迟测量**（`crates/kanami-net/src/clock.rs`）
- 用 Ping-Pong 四点时间戳估算两端时钟偏移（NTP 简化版）
- 保留最近 16 次采样，取往返最快的那次——路径最干净，估计最可信
- 同步之后才能把「发送端采集时刻」换算到本机时间轴，算出真实延迟
- 上一次交付里显示的只是本地缓冲时间，现在能给出端到端数字

**Android 前台服务**（`PlaybackService.kt`）
- 常驻通知 + 停止按钮，锁屏/切后台不再断流
- `foregroundServiceType="mediaPlayback"`（Android 14 要求）
- 已验证：`dumpsys activity services` 能看到 `ServiceRecord{... .PlaybackService}`

**Rust 侧入口已接上**（本轮补完）：
- `src-tauri/src/playback_service.rs`，用 JNI 调 Kotlin 的静态方法
- 连上音源时启动服务（通知标题带对端设备名），断开且无音源时停止
- 只在 `cfg(target_os = "android")` 下编译，桌面构建完全不受影响
- 用 jni 0.21 而不是 0.22：0.22 把 JNIEnv 拆成 Env/EnvUnowned 变成回调式 API，
  而我们只需要「附加线程 → 调静态方法」这个最简单的用法
- `lib.rs` 的 `forbid(unsafe_code)` 改成 `deny`：forbid 无法被子模块覆盖，
  而这个模块必须用 unsafe 才能做 JNI。每处 unsafe 都写了安全不变量。

## 环境备注

**Android 构建必须用环境变量**：Tauri CLI 会覆盖 `.cargo/config.toml` 里的 linker，只有 `RUSTFLAGS="-C linker=.../aarch64-linux-android26-clang"` 能压住。不带 API 26 会因找不到 `-laaudio` 链接失败。

**模拟器很脆**：反复安装/卸载会把 PackageManager 弄坏（`INSTALL_FAILED_VERIFICATION_FAILURE` / `Failed to open an IncFS file`）。恢复办法：`adb reboot`，等 `getprop sys.boot_completed` 返回 1。

## 本轮（第 1 轮续）新增修复

### ✅ 修掉的真 bug：多音源连接会互相覆盖

`connect_to_peer` 里把 `stream_id` 写死成 1，接收线程又把所有来的包投给 `incoming` 列表的 `first_mut()`。**接第二台音源时，两路数据会挤进同一路抖动缓冲**——「一播放端接多音源」这个核心需求实际上是坏的。

修法：`AppState` 加 `next_stream_id` 原子分配器，每路一个新号；接收线程按 `stream_id` 精确定位；`disconnect` 按 `device_id` 找到对应那一路再移除。补了 3 个回归测试锁住行为。

### ✅ 修掉的 CI 问题（三层，逐个击破）

1. `actions/setup-node` 的 `cache: pnpm` 要求它自己探测 pnpm store，在 pnpm 刚装好没 install 过时探测失败 → 改用 `actions/cache@v4` 显式缓存 store。
2. pnpm 12 默认阻止依赖执行安装脚本，esbuild 的 postinstall 被拦 → `pnpm install --frozen-lockfile` 报 `ERR_PNPM_IGNORED_BUILDS` → 在 `pnpm-workspace.yaml` 的 `allowBuilds` 里放行 esbuild。
3. 修复后本地 `pnpm install --frozen-lockfile` 与 `pnpm build` 均通过。

**CI 当前状态**：最新一次运行仍在 GitHub 队列里等 runner（免费额度高峰），不是失败。
